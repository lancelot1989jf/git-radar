# CODEX Engineering Rules

## 1. 目标

你在本项目中的所有开发、修改、重构、修复任务，必须优先从“工程可维护性、低耦合、可复用、可验证”的角度执行，而不是只追求功能暂时可用。

你的输出必须服务于长期维护，而不是短期堆砌。

---

## 2. 核心工程原则

### 2.1 优先遵守现有工程结构
在开始任何修改前，必须先阅读并理解当前工程已有的目录结构、模块边界、命名方式、已有公共方法、已有数据流和调用关系。

禁止在未确认现有结构的前提下：
- 新建重复能力的工具类
- 新建重复能力的 service / manager / helper
- 在错误的层级放置逻辑
- 绕过已有模块直接硬连代码

### 2.2 优先复用真实存在的公共能力
如果项目中已经存在可复用的公共方法、工具类、封装层、基类、组件、客户端、适配器，必须优先复用。

禁止：
- 假装项目里已有某个公共方法
- 凭空调用不存在的方法
- 为了省事复制粘贴已有逻辑到新位置
- 同一逻辑在多个文件中重复实现

如果怀疑项目中可能已经有公共实现，必须先搜索确认，再决定是否新增。

### 2.3 降低耦合度
新增代码必须尽量降低以下耦合：
- UI 与业务逻辑耦合
- 业务逻辑与网络实现耦合
- 平台层与业务层耦合
- 模块之间双向依赖
- 单个页面直接依赖多个底层细节

优先采用：
- 单向依赖
- 接口清晰的中间层
- 小范围局部改动
- 依赖注入或现有注入方式
- 明确的数据结构传递

### 2.4 控制复杂度
禁止把过多逻辑塞进：
- 单个方法
- 单个 Widget / ViewController / Activity
- 单个 ViewModel / Controller
- 单个工具类

必须遵守：
- 单个方法尽量只做一件事
- 方法过长时拆分为私有小方法
- 复杂条件分支要提炼
- 重复逻辑要归纳
- 状态变更和副作用要分离

### 2.5 只使用真实存在的能力
你不能假设项目中存在任何类、方法、字段、常量、配置、接口、路由、资源文件、第三方依赖。

必须先检查代码，再使用。

如果不存在：
- 先明确指出不存在
- 再给出最小化新增方案
- 保持与现有风格一致
- 不要编造调用链

### 2.6 最小化改动优先
对于已有功能的修改，优先采用最小必要改动，而不是大范围重构。

除非任务明确要求重构，否则禁止：
- 无必要地改文件结构
- 无必要地改命名
- 无必要地改调用链
- 无必要地迁移层级
- 顺手改 unrelated code

### 2.7 保证可验证性
所有修改都必须能被人工快速验证。

输出时必须说明：
- 改了哪些文件
- 每个文件为什么要改
- 是否涉及接口/数据结构变化
- 是否影响现有调用方
- 如何验证
- 有哪些风险点

## 3. 强制执行规则

### 3.1 修改前必须做的事
在写代码前，必须先完成以下检查：

1. 阅读相关文件，不可只看单个文件
2. 理解当前调用链
3. 搜索是否已有相似能力
4. 确认依赖方向是否合理
5. 确认新增逻辑放在哪一层最合适
6. 确认是否能复用现有模型/方法/组件
7. 确认不会制造重复实现

如果以上任一项未确认，不要直接开始写实现。

### 3.2 输出代码时必须遵守
输出方案时必须优先提供以下其中一种：

#### 方案 A：最小补丁
适用于小改动：
- 明确指出修改文件
- 明确指出插入位置
- 明确指出替换范围
- 不扩散修改面

#### 方案 B：完整替换文件
适用于中等复杂度修改：
- 提供完整文件
- 保持现有 import、命名风格、层级结构一致
- 不引入无关重构

#### 方案 C：先设计后落地
适用于复杂任务：
- 先输出模块设计
- 再输出改动点
- 最后输出代码

禁止直接给出“想当然”的伪实现。

### 3.3 方法设计规则
新增或修改方法时必须满足：
- 方法职责单一
- 参数数量尽量少且清晰
- 命名必须表达真实意图
- 避免超长方法
- 避免多层嵌套 if/else
- 避免方法同时承担：校验 + 计算 + IO + 状态更新 + UI 刷新
- 公共逻辑优先下沉
- 私有逻辑不要伪装成公共工具

如果一个方法已经过于复杂，优先拆分，不要继续堆逻辑。

### 3.4 复用规则
发现已有可复用逻辑时，必须优先选择：
1. 直接复用现有方法
2. 小幅扩展现有方法
3. 提炼公共部分后复用
4. 最后才新增全新实现

禁止：
- 为了局部方便复制已有逻辑
- 建立“看起来通用、实际上只用一次”的伪公共方法
- 把业务特定逻辑硬塞进真正的公共层

### 3.5 耦合控制规则
必须避免以下情况：
- UI 页面直接拼接网络请求细节
- 页面直接处理复杂业务分支
- ViewModel 直接关心平台实现细节
- 插件层直接耦合业务页面
- 底层工具类引用上层业务对象
- 为了快速完成而跨层调用

必须尽量保持：
- UI 层负责展示和用户交互
- ViewModel / Controller 负责状态编排
- Data / Client 层负责数据获取
- Platform / Native 层负责平台能力
- 公共工具只做通用能力，不侵入业务

### 3.6 禁止假设存在
你不能出现以下行为：
- “假设项目里有一个 commonUtils”
- “假设这里已经有统一日志方法”
- “假设这里已有 refreshToken 流程”
- “假设这里有公共扫描配置类”
- “假设这里已有统一错误处理器”

如果没有看到真实代码，就不能这样写。

当不存在时，应输出：
- 当前项目中未发现该能力
- 建议新增在什么位置
- 为什么放这里最合理
- 最小实现方式是什么

### 3.7 不要使用 YOLO 探测
除非任务明确要求并且项目明确已有相关依赖与方案，否则禁止默认引入 YOLO 相关探测、识别、推理方案。

禁止：
- 把 YOLO 当成默认视觉检测方案
- 未经确认就建议引入 YOLO 模型
- 在文档扫描、边缘检测、轻量端侧任务中默认替换为 YOLO

必须先基于当前项目真实技术栈和现有实现判断。

### 3.8 重构规则
当任务涉及重构时，必须遵守：
- 先说明当前问题
- 再说明为什么需要重构
- 再给出最小可行重构方案
- 明确重构边界
- 不能无限扩散

如果当前代码只是“丑”，但没有明显工程问题，优先不重构。

只有在以下情况才建议重构：
- 重复逻辑明显
- 方法复杂度失控
- 调用链混乱
- 依赖方向错误
- 未来需求会持续叠加
- 当前结构已经明显阻碍维护

## 4. 输出格式要求

### 4.1 先给工程判断
先说明：
- 当前问题属于哪一层
- 是否应复用现有结构
- 是否需要新增公共能力
- 是否需要拆分方法
- 是否存在耦合风险

### 4.2 再给改动策略
必须说明：
- 为什么这样改
- 为什么不是另一种改法
- 改动范围控制在哪里
- 是否兼容现有逻辑

### 4.3 再给代码
代码必须：
- 与现有项目风格一致
- 不伪造不存在的方法
- 不引入无关依赖
- 不偷换架构层级

### 4.4 最后给验证方式
必须说明：
- 如何编译/运行
- 如何验证功能
- 如何验证未破坏旧逻辑
- 风险点在哪里

---

## 5. 自检清单
在输出最终代码前，你必须自检以下问题：
- 是否真的看过相关现有代码？
- 是否复用了真实存在的公共能力？
- 是否避免了重复实现？
- 是否避免了跨层耦合？
- 是否避免了假设方法存在？
- 是否避免了单个方法过长？
- 是否把复杂逻辑拆分清楚？
- 是否控制了改动范围？
- 是否说明了验证方法？
- 是否引入了不必要的新抽象？
- 是否误用了 YOLO 或默认推荐 YOLO？
- 是否输出了能直接落地的结果，而不是空泛建议？

若任一答案是否定，继续修正，不要直接结束。

---

## 6. 与本项目相关的特殊约束

### 6.1 必须尊重现有分层
本项目中，修改必须尽量遵守现有分层与模块职责，不要把职责打乱。

例如：
- UI 层不要承载过多业务逻辑
- ViewModel/状态层不要直接侵入底层平台细节
- Data/Client 层不要耦合 UI 表现
- 原生插件层不要直接写业务页面逻辑

### 6.2 Flutter 与原生插件边界必须清晰
涉及 Flutter 主工程与原生插件联动时，必须明确区分：
- Flutter 侧接口
- MethodChannel 或桥接层
- Android/iOS 原生实现
- 平台差异处理
- 返回值协议

禁止在两侧同时堆叠重复逻辑。

### 6.3 配置、接口、常量必须先确认
凡是涉及：
- 服务端地址
- token
- 登录流程
- channel 名称
- JSON 字段
- 路由
- 页面参数
- native 返回字段

都必须先确认真实实现，不允许想当然。

---

## 7. 当信息不足时的处理方式
当你发现信息不足时，不要编造答案。

你应该：
1. 明确说明当前缺失什么
2. 基于现有代码给出最保守方案
3. 标明哪些地方需要进一步确认
4. 在不确定处避免写死伪实现

---

## 8. 最终原则
你的目标不是“尽快写出能跑的代码”，而是“在当前工程里写出最合理、最可维护、最少副作用的代码”。

始终优先：
- 工程一致性
- 真实代码依据
- 低耦合
- 可复用
- 小方法
- 小改动
- 可验证
- 可维护
